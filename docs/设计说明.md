# 设计说明：几个踩过的坑

这份文档记录的都不是「我觉得应该这样」，而是**线上真实炸过**之后改出来的。每条按「现象 → 根因 → 做法」写。

---

## 1. 群里的 @ 分隔符不是空格

**现象**：私聊 `/签到` 正常，群里 `/签到` 没反应，直接落到大模型，模型回一句「我没有这个功能」。

**根因**：微信群里 @ 人时，昵称和正文之间的分隔符是 **U+2005（FOUR-PER-EM SPACE）**，不是 ASCII 空格：

```
"@小助手\u2005/签到"
```

旧实现用 `text.partition(" ")` 切，切不动 → 推给 AstrBot 的正文仍然是 `@小助手\u2005/签到`。而 AstrBot 判断「这是不是指令」看的是 `message_str` 是否以 `wake_prefix`（`/`）开头 —— 开头是 `@`，永远不匹配。

**做法**：`mentions.py` 里的 `MENTION_SEPS` 覆盖 U+2005 及同类空白（NBSP、EM SPACE、全角空格等）。解析逻辑单独成文件，不带 `wxhook` 依赖，可以离线单测。

对应测试：`tests/test_mention_split.py`。

## 2. OneBot 的 `user_id` 必须跨重启稳定

**现象**：AstrBot 每次重启后，同一个人变成「新用户」，对话记忆、人设、好感度全部归零。

**根因**：用 Python 的 `hash(str)` 把 wxid 映射成整数。Python 3 的字符串 hash **每个进程都不同**（有随机盐），所以映射一次一个样。

**做法**：`crc32(wxid) & 0x7FFFFFFF`，确定性映射。同时把 `id ↔ wxid` 落盘到 `wxid_map.json`，这样即使还没收到新消息，也能回复老会话。

## 3. 图片：三个连续踩的坑

### 3.1 默认 1 MiB 单帧上限会把连接掐掉

AstrBot 的 `aiocqhttp` 适配器会把 `Image` 段统一转成 `base64://` 内嵌。一张 1 MB 的原图 base64 后约 1.33 MB，整条 `send_private_msg` 的 JSON 就超过 `websockets` 默认的 1 MiB。

它不会截断，而是**发一个 1009 帧把整条连接关掉** —— 图片丢了，连接也断了，日志看起来像「网络问题」。

**做法**：`ws_max_size` 抬到 64 MiB。

### 3.2 `download_attachment` 是「先返回、后落盘」

群里的事件通常**不带** `base64Img`（私聊一般带），只能让 DLL 把附件落地再读。但 `download_attachment(msgId)` 返回时文件往往还没写完，而且**不在返回值里给路径** —— 它写死在 `<dataSavePath>\wxhelper\image\<msgId>.dat`。

**做法**：返回后轮询目录，等到文件大小连续两次采样一致（写稳了）再读。

### 3.3 大图是分块落盘的

目录里会先出现 `<msgId>.dat<十六进制串>` 这种 512 KB 的**分块文件**，它不是图片。用 `<msgId>*` 宽松匹配会优先抓到它，发给模型 → `400 You have uploaded an unsupported image`。

**做法**：只认精确文件名（`<msgId>.dat` / `.jpg` / …），并且校验文件头确实是 JPEG/PNG/GIF/WEBP。

对应测试：`tests/test_bridge_image_flow.py`。

## 4. 群 @ 判定：别靠正文猜

**现象**：群里 `@张三 你昨天说的那个` —— 机器人也回。它以为被叫了。

**根因**：正文里的 `@昵称` 只是一段纯文本，光看文本无法区分「@我」和「@别人」。旧逻辑只要开头有 `@`，就伪造一个指向机器人的 `at` 段，AstrBot 见状就回复。

**做法**：权威来源是事件 `signature` 里的 `msgsource.atuserlist`（逗号分隔的 wxid 列表）。只有 `self_wxid` 在其中，才认为被唤醒。

`bot_nicknames` 只在 `atuserlist` 缺失时兜底。

## 5. 发文件 / 发图片不能发完立刻删

**现象**：16.8 MB 的 wav 发出去，微信里立刻显示「发送中断」。

**根因**：`sendFileMsg` / `sendImagesMsg` 只是把上传任务丢给 DLL 就返回 `code=1`，真正上传还在后台跑。源文件一删，上传就断。

**做法**：`_cleanup_later()` 用定时器延迟删除，默认 `send_file_keep_seconds = 1800`。启动时再扫一遍超过 6 小时的遗留临时文件。

---

## 6. `ready.json`：未登录时发送也会「成功」

**现象**：微信还没登录，脚本就发消息，日志显示 `code=1 msg=success`，但对方什么也没收到。

**根因**：`wxhook` 的 `send_*` 在未登录状态下照样返回成功码。

**做法**：登录成功后写一个 `ready.json`（含 wxid、昵称、时间）。外部程序（比如 AstrBot 的启动致辞插件）轮询它，比看返回值可靠。

同理，进程看门狗发现微信退出时会撤销这个文件。

## 7. 关于 `x64 → x32` 内存补丁

早期为了绕过「版本过低」，做过一个把微信进程内存里的 `x64` 字符串改成 `x32` 的补丁（`patch_audit.py`）。

单独用它，结论是**没用，而且有害**：

| 做法 | 结果 |
| --- | --- |
| 只做版本伪装（faker） | ❌ 版本过低 |
| 按评分挑选，只改 10~13 处 | ❌ 版本过低 |
| 全部 57 处都改 | ❌ 仍然版本过低 |
| 打开补丁跑一段时间 | ❌ 约每小时随机崩溃一次 |

崩溃特征：

```
出错模块 : unknown     ← 执行流跳到非法地址
异常代码 : 0xc0000005  ← 访问冲突
事件名称 : BEX64       ← 控制流异常
```

### 但「伪装 + 补丁」一起开，它真的能过门禁

2026-10-23 的对照实验把这件事钉死了（微信 3.9.5.81 / 两台机器）：

| `faked_version` | `patch_x64_to_x32` | 结果 |
| --- | --- | --- |
| 空（faker 被删，未伪装） | true | ❌ 版本过低，微信被关 |
| `3.9.12.51`（运行时全量替换 6/6） | **false** | ❌ 版本过低，弹窗在扫码前 |
| `3.9.12.51`（faker SUCCESS） | **true**（39 处） | ✅ 登录成功 |
| `3.9.12.51`（faker SUCCESS） | **true**（37 处） | ✅ 登录成功 |

配合的扫码顺序也是必要条件（单打补丁按正常顺序扫照样被拒）：

1. 微信停在扫码界面
2. 打全量 `x64 → x32` 补丁
3. 手机扫码 → **先不要点确认**
4. 再扫一次
5. 点确认登录

推测是第二次扫码时客户端的版本特征已经变了，服务端那一步校验被跳了过去。

补丁来自 [alingalingling/Astrbot-wechat-bot-](https://github.com/alingalingling/Astrbot-wechat-bot-) 的 `wechat_patcher.py`。

### 所以现在的默认值是「两个都开」

配置文件模板里 `patch_x64_to_x32` 默认 `true`，`options.normalize()` 还会在启动时把「只开一半」补齐 —— 因为它俩不是一个可选优化项，是**同一个门禁条件的两个必要条件**。

代价是：开着补丁跑会话恢复，大约每小时会崩一次。现在 `require_patch_and_faker: false` 可以让你在过了门禁之后手动关掉，而不会被自动补回来。

### 补丁现在会改页保护（2026-10-23 修）

旧 `patch_audit.py` 写死了「Never changes page protections」，于是只读页一律写不进去：

```
candidates=52  verified=30  write_failed=20     ← 全部 GetLastError 998
                                               (ERROR_NOACCESS = 只读页)
```

能过门禁的机器是「恰好门禁依赖的那处可写」，换台机器内存布局一变就可能变成「日志显示补丁跑完了、实际没打上」。

现在每个站点的写入流程是：

1. `VirtualProtectEx(local, page, PAGE_READWRITE)`
2. 写 3 字节
3. 回读校验
4. `finally` 里 `VirtualProtectEx(原保护)` 恢复

审计里逐站点记 `protect_before` / `page_unlocked` / `protect_restored`，`write_failed` 也按原因分了桶：

| 桶 | 含义 |
| --- | --- |
| `write_failed_protect` | 已放开写保护，但写还是报 998 —— 真的没写进去 |
| `write_failed_reprotect` | 连 `VirtualProtectEx` 都没成功（权限/句柄） |
| `write_failed_other` | 其他写入异常 |

`wcprobe.dll+0x26A6DD` 的跳过逻辑原样保留 —— 那是崩溃可疑点。

## 7.1 为什么要自己调 faker，而不是 `Bot(faked_version=…)`

**现象**：`logs/bridge.log` 里只有一句 `构造 wxhook Bot(版本伪装 -> 3.9.12.51)`，而 `SUCCESS wechat version faked: 3.9.5.81 -> 3.9.12.51` 只出现在控制台。

**根因**：wxhook 用的是 **loguru**，跟桥接的 `logging` 是两套；它的 sink 只写 `sys.stdout`。于是文件日志里分不清「伪装没执行 / 执行了但失败 / 成功但门禁仍拦」—— 排障时在这一步绕了很久。

**做法**（两条一起）：

1. 构造 `Bot` 时**不**传 `faked_version`，而是在 `on_start` 里显式调 `fake_wechat_version()`，把返回码写进 `bridge.log`；
2. 给 loguru 加一个文件 sink（`attach_wxhook_logger()`），把 wxhook 自己的日志也以 `WXHOOK | …` 前缀写进 `bridge.log`。

注意 loguru 的 `format` 里 `{…}` 全是格式化字段 —— 想输出字面量 `WXHOOK` 就得写死成普通文本，写成 `{'WXHOOK':<8}` 会让每次日志调用都抛 `KeyError`。

## 7.2 端口：别写死 11229，也别写死 6199

**现象**：

```
正在连接 AstrBot: ws://127.0.0.1:11229/ws
WARNING 连接断开或失败([WinError 1225] 远程计算机拒绝网络连接。),5 秒后重连
netstat 只有 0.0.0.0:6199 LISTENING
```

**根因**：桥接默认 11229（AstrBot 3.x），而本机 AstrBot 4.29.1 的 aiocqhttp 在 6199。不是防火墙、不是 `/ws` 路径、不是 token。

**做法**：两件事一起做。

1. 默认值改成 6199（4.x），但**推荐省端口**：`ws://127.0.0.1/ws` → `preflight.resolve_ob_url()` 自动探测 11229 / 6199，日志打印实际用的端口；
2. `WinError 1225` 不再只输出「连接断开」，而是直接提示「端口上没有服务在监听，去 WebUI → 平台 → aiocqhttp 看端口」。

**不偷偷换端口**：用户明确写了端口就只用那个。写错时日志直说「端口 X 上没有服务在监听」—— 偷偷换成别的，会让日志和实际连接对不上，排障反而更乱。

## 7.3 启动前自检：把「半小时后才发现的错」拿到第一秒

`preflight.py` 只依赖标准库（要在 webhook / websockets / pymem 装好之前就能跑），做这些只读检查：

| 检查 | 不做会怎样 |
| --- | --- |
| `IsUserAnAdmin()` | 注入失败，报错是含糊的「拒绝访问」 |
| 端口探测 | `WinError 1225` 循环重连，看不出是端口错 |
| `faker.exe` 存在 / 可读 / SHA256 | 微信根本起不来，堆栈埋在 wxhook 里 |
| `WeChat.exe` 是否在跑 | 撞 `Exception: port occupied:19001` |
| `tools/wxhook.json` 端口账本 | 端口莫名变 19002，DLL 的 `config.ini` 却固定在 19001 |

一个细节：`find_wxhook_dirs()` 用 `importlib.util.find_spec("wxhook")` 问「当前环境到底加载的是哪一份」，而不是猜 uv 缓存里最新的一份 —— uv 缓存里常存着好几个解包目录，猜错就会盯着一份残留副本报「faker 不存在」。

## 7.4 微信会自己升级掉，而我们从来看不到原因

**现象**：启动后 1 秒就结束，日志只有：

```
构造 wxhook Bot(版本伪装 -> 3.9.12.51,由桥接显式调用 faker)
ERROR wechat | 微信侧启动失败
Exception: unknown error
```

**根因链**（2026-10-23 两轮实测）：

1. 微信在后台把自己从 3.9.5.81 升到 3.9.12.55 —— **同一天两次**，
   不需要用户确认、不需要重启电脑；
2. wxhook 0.0.10 把版本写死在 `core.py`；
3. `start-wechat.exe` 注入失败只回 `1,unknown error`，`core.py:77` 原样
   `raise Exception(output)`，于是所有信息都没了；
4. 失败发生在 `Bot(...)` 构造里，`on_start` 没执行 —— faker 和补丁这轮
   压根没跑。

**最讽刺的一点**：`preflight.py` 里早就定义了 `SUPPORTED_WECHAT_VERSION`，
但**全仓库零引用**。自检查了端口、权限、faker、端口残留，唯独没查
“装的到底是不是 3.9.5.81”。

**做法**：

- 新增 `wechat_version.py`：注册表 `Version` → FileVersion → 目录名，三级回退；
- 自检把它当成阻塞项：版本不对就不启动，并打出恢复步骤；
- `start-wechat.exe` 的文案分类（`unknown error` / `port occupied` / `dll not found`），
  分别给可执行提示；
- 新增 `--doctor`，`start.bat` 启动前先跑，不过就停。

**顺带踩到的两个 Windows 坑**（都写进了代码注释与单测）：

| 坑 | 后果 |
| --- | --- |
| PowerShell 里 `Get-ChildItem 'C:\WeChat\[3.9.5.81]'` 把方括号当字符类 | **静默返回 0 条**，会误报“版本目录是空的”。必须 `-LiteralPath`；Python 的 `os.scandir` 天然按字面量 |
| 暂存目录是 `[3.9.12.55]_tmp`，**不以下方括号结尾** | 只判断“`[` 开头 `]` 结尾”会把最重要的升级信号漏掉。单测抓到的 |

## 8. 为什么走 OneBot v11，而不是写 AstrBot 原生适配器

原生平台适配器可以拿到 OneBot 表达不了的东西（撤回、合并转发、名片、小程序卡片……），但代价是：

- 要跟着 AstrBot 的内部 API 走，AstrBot 一改就断
- 只能给 AstrBot 用，接不了 NoneBot / Koishi / 其它 OneBot 框架

OneBot v11 是 AstrBot 官方支持的协议，桥这头只管把微信事件翻译成标准事件，框架那头换谁都行。**多一层协议，少一层绑定。**

代价是：`record`（语音）只能降级成文件，`reply` 段只能拍平成文本 —— 因为 OneBot 的表达能力就到这儿。
