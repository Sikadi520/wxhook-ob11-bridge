# 设计说明：几个踩过的坑

这份文档记录的都不是「我觉得应该这样」，而是**线上真实炸过**之后改出来的。每条按「现象 → 根因 → 做法」写。

---

## 1. 群里的 @ 分隔符不是空格

**现象**：私聊 `/签到` 正常，群里 `/签到` 没反应，直接落到大模型，模型回一句「我没有这个功能」。

**根因**：微信群里 @ 人时，昵称和正文之间的分隔符是 **U+2005（FOUR-PER-EM SPACE）**，不是 ASCII 空格：

```
"@小助手\u2005/签到"
```

旧实现用 `text.partition(" ")` 切，切不动 → 推给 AstrBot 的正文仍然是 `@小助手\u2005/签到`。而 AstrBot 判断「这是不是指令」看的是 `message_str` 是否以 `wake_prefix`（`/`）开头 —— 开头是 `@`，永远不匹配。

**做法**：`mentions.py` 里的 `MENTION_SEPS` 覆盖 U+2005 及同类空白（NBSP、EM SPACE、全角空格等）。解析逻辑单独成文件，不带 `wxhook` 依赖，可以离线单测。

对应测试：`tests/test_mention_split.py`。

## 2. OneBot 的 `user_id` 必须跨重启稳定

**现象**：AstrBot 每次重启后，同一个人变成「新用户」，对话记忆、人设、好感度全部归零。

**根因**：用 Python 的 `hash(str)` 把 wxid 映射成整数。Python 3 的字符串 hash **每个进程都不同**（有随机盐），所以映射一次一个样。

**做法**：`crc32(wxid) & 0x7FFFFFFF`，确定性映射。同时把 `id ↔ wxid` 落盘到 `wxid_map.json`，这样即使还没收到新消息，也能回复老会话。

## 3. 图片：三个连续踩的坑

### 3.1 默认 1 MiB 单帧上限会把连接掐掉

AstrBot 的 `aiocqhttp` 适配器会把 `Image` 段统一转成 `base64://` 内嵌。一张 1 MB 的原图 base64 后约 1.33 MB，整条 `send_private_msg` 的 JSON 就超过 `websockets` 默认的 1 MiB。

它不会截断，而是**发一个 1009 帧把整条连接关掉** —— 图片丢了，连接也断了，日志看起来像「网络问题」。

**做法**：`ws_max_size` 抬到 64 MiB。

### 3.2 `download_attachment` 是「先返回、后落盘」

群里的事件通常**不带** `base64Img`（私聊一般带），只能让 DLL 把附件落地再读。但 `download_attachment(msgId)` 返回时文件往往还没写完，而且**不在返回值里给路径** —— 它写死在 `<dataSavePath>\wxhelper\image\<msgId>.dat`。

**做法**：返回后轮询目录，等到文件大小连续两次采样一致（写稳了）再读。

### 3.3 大图是分块落盘的

目录里会先出现 `<msgId>.dat<十六进制串>` 这种 512 KB 的**分块文件**，它不是图片。用 `<msgId>*` 宽松匹配会优先抓到它，发给模型 → `400 You have uploaded an unsupported image`。

**做法**：只认精确文件名（`<msgId>.dat` / `.jpg` / …），并且校验文件头确实是 JPEG/PNG/GIF/WEBP。

对应测试：`tests/test_bridge_image_flow.py`。

## 4. 群 @ 判定：别靠正文猜

**现象**：群里 `@张三 你昨天说的那个` —— 机器人也回。它以为被叫了。

**根因**：正文里的 `@昵称` 只是一段纯文本，光看文本无法区分「@我」和「@别人」。旧逻辑只要开头有 `@`，就伪造一个指向机器人的 `at` 段，AstrBot 见状就回复。

**做法**：权威来源是事件 `signature` 里的 `msgsource.atuserlist`（逗号分隔的 wxid 列表）。只有 `self_wxid` 在其中，才认为被唤醒。

`bot_nicknames` 只在 `atuserlist` 缺失时兜底。

## 5. 发文件 / 发图片不能发完立刻删

**现象**：16.8 MB 的 wav 发出去，微信里立刻显示「发送中断」。

**根因**：`sendFileMsg` / `sendImagesMsg` 只是把上传任务丢给 DLL 就返回 `code=1`，真正上传还在后台跑。源文件一删，上传就断。

**做法**：`_cleanup_later()` 用定时器延迟删除，默认 `send_file_keep_seconds = 1800`。启动时再扫一遍超过 6 小时的遗留临时文件。

---

## 6. `ready.json`：未登录时发送也会「成功」

**现象**：微信还没登录，脚本就发消息，日志显示 `code=1 msg=success`，但对方什么也没收到。

**根因**：`wxhook` 的 `send_*` 在未登录状态下照样返回成功码。

**做法**：登录成功后写一个 `ready.json`（含 wxid、昵称、时间）。外部程序（比如 AstrBot 的启动致辞插件）轮询它，比看返回值可靠。

同理，进程看门狗发现微信退出时会撤销这个文件。

## 7. 关于 `x64 → x32` 内存补丁

早期为了绕过「版本过低」，做过一个把微信进程内存里的 `x64` 字符串改成 `x32` 的补丁（`patch_audit.py`）。

**结论：没用，而且有害。**

| 做法 | 结果 |
| --- | --- |
| 只做版本伪装（faker） | ❌ 版本过低 |
| 按评分挑选，只改 10~13 处 | ❌ 版本过低 |
| 全部 57 处都改 | ❌ 仍然版本过低 |
| 打开补丁跑一段时间 | ❌ 约每小时随机崩溃一次 |

崩溃特征：

```
出错模块 : unknown     ← 执行流跳到非法地址
异常代码 : 0xc0000005  ← 访问冲突
事件名称 : BEX64       ← 控制流异常
```

**所以默认关闭**（`patch_x64_to_x32: false`）。保留代码只是为了留个记录，不建议任何人打开。

真正的原因在第 2 条硬约束里：**门禁在服务端，本地怎么改内存都没用**。

## 8. 为什么走 OneBot v11，而不是写 AstrBot 原生适配器

原生平台适配器可以拿到 OneBot 表达不了的东西（撤回、合并转发、名片、小程序卡片……），但代价是：

- 要跟着 AstrBot 的内部 API 走，AstrBot 一改就断
- 只能给 AstrBot 用，接不了 NoneBot / Koishi / 其它 OneBot 框架

OneBot v11 是 AstrBot 官方支持的协议，桥这头只管把微信事件翻译成标准事件，框架那头换谁都行。**多一层协议，少一层绑定。**

代价是：`record`（语音）只能降级成文件，`reply` 段只能拍平成文本 —— 因为 OneBot 的表达能力就到这儿。
